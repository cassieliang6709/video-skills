# 逐字稿写作规范

## 受众默认值
会 Python、相关课程基本忘光了的大学生（2026-10-24 更新）。写法的总原则见 `kepu-style.md`：先具体后抽象，"如果让你来设计"，
一张物理图贯穿全片，术语预算，类比只讲一个点，细节放进进阶章。
**不要解释**：Python 语法、for 循环、函数调用这类写过代码就会的常识。
用户另行指定受众时以用户为准，并写进 script.md 的 front matter。

## 第一原则：每句话都必须带来新信息
写完每一句都问：删掉它，观众会少懂什么？答案是"什么都不少"就删。
常见的多余表述（都要删）：
- 预告和过渡套话："接下来我们来看……""好，回到正题""这一点非常重要""我们先花几分钟……"
- 重复屏幕上已经显示的东西：把代码逐字念一遍、把形状 (2, 3, 10, 5) 念成"2、3、10、5"再解释一遍
- 对同一件事的第二种说法："也就是说……换句话说……"
- 显而易见的细节：PyTorch 从 0 开始计数、每行加起来等于 1 这种画面上一眼可见的
- 过度铺垫的比喻：比喻只讲一个点，一个概念最多一个，讲清就收
- 无信息的情绪词："非常关键""很神奇""大家一定要记住"

## 每集的结构：总—分—总
- 总：开头先抛出本集要回答的问题，再列出本集的小节（"这一集讲三件事：……"），不超过 20 秒。
- 分：按小节顺序展开，每节开头一句话说明这一节解决地图里的哪一项。
- 总：结尾每节一句话收回结论（只说结论，不复述过程），再一句预告下一集。
- 总的部分也要遵守"每句话都带来新信息"：地图是给观众的导航，不是套话。

## 借鉴 RethinkFun 的讲法（详见 rethinkfun-style.md）
- 开场二选一：拆论文标题当大纲；或者连抛 3–4 个"你知道……吗？"，每个问题对应本集一节。
- 先把朴素做法一步一步讲透（必要时讲到数据在显存里怎么搬），问题自然暴露，再讲改进。
- 主动说明简化："为了讲解方便，这里先不考虑多头和 batch。"
- 难点先跳过、标明后面单独讲；每节结尾用"看起来都不错，除了……"指出剩下的问题，引出下一节。
- 每个方案先一句目标，再"通过以下 N 点实现"，然后逐点展开。
- 每章至少一个自问自答（"为什么是 4？"），问完马上回答。
- 用真实模型的规模举例（层数、头数、序列长度），并把乘法算给观众看。
- 前置知识不重讲，说一句"不清楚的话可以看第 X 集"。
- 结尾：一句话列出本期讲了什么 → 下期预告 → 点赞关注 → 代码和论文链接在简介里。

## 开头公式（借鉴 Cishoon《图解 PyTorch 编译器》，分析见 cishoon-style.md）
1. **0–6 秒结果预告**：把整集的结论用几个快速画面演一遍（原始输入 → 中间步骤 → 最终结果），配标题，不解释。
2. **一个反常的事实或数据**（带出处或实测）：让观众觉得"不对啊，为什么？"。例如"99.8% 的计算量只占 61% 的时间"。
3. **一句话问题**，并且**结尾才回答**。开头只抛问题、不给答案，中间所有内容都在为它铺路。
4. **贯穿全片的例子**：一个小例子从头用到尾，尽量不中途换例子。
5. **值得看的理由**：一个真实数字（官方实测快了多少、省了多少）。
6. **路线图 + 门槛声明**："分三步……""这期只需要你会……"。

## 节奏：每 1.5–2.5 分钟一个高潮点，类型轮换（8–12 分钟的长集更要守住，不然会拖）
不追求画面每几秒都变，追求**每隔一段时间有一个让人想继续看的点**。可用的类型：
- **先猜再揭晓**："先猜一下，这要多久？"→ 估算 → 实测
- **画面里计数**：一趟一趟数（搬运次数、合并次数），计数器跳动
- **让观众参与**："假设你来写，你会怎么改？"
- **替观众提问**："你可能会问：为什么不……？"
- **真实运行**：终端里真的跑一次，看到第一次慢、之后快这类现象
- **实测结果对比**：改进前后的耗时条形图并排
- **回到开头**：中段或结尾回扣开头的问题
写完逐字稿后，按时间标出每个高潮点的位置，相邻两个间隔超过 2.5 分钟就补一个。

## 术语与门槛
- **术语预算**：每集新术语不超过 6 个，每句只推进一个点；寄存器、源码级的名词只在进阶章出现（kepu-style.md）。
- **先讲概念，再给名字**："GPU 上运行的这种程序，叫 kernel。"名字出现时只用一句大白话解释。
- 术语第一次出现前，观众必须已经看到它指代的东西；不要先抛名词再解释。
- **主动减负**：只需要记住名字的东西明说"今天只需要记住这个名字和它干的这一件事"。
- **先画物理模型**：涉及硬件或内存时，先画出"数据在哪、在哪里算、怎么搬"，后面都回到这张图。
- **过程要演出来**：说"把 X 变成 Y"时，必须演示怎么变（例如 UTF-8 要演示编号的二进制怎么填进字节模板），不能只给输入和输出。

## 结尾公式
1. 回到开头的问题，用一两句话正面回答。
2. 本集做了哪几件事，每件一句结论，对应到名字。
3. **列出今天跳过的问题，每个指向后面的某一期**（"这个第 3 期讲"），制造追更的理由。
4. 下期预告 + 求三连。

## 讲解顺序
- 从 0 到 1：每章只引入一个新概念，先给动机（问题是什么、朴素做法哪里不行），再给方案。
- 一个贯穿全片的小例子（小尺寸、数值可见），之后再换成真实模型的规模计算。
- 讲到"为什么"就停：解释到观众能自己推出结论即可，不展开到实现细节以外的旁支。
- **推导章末尾加一个小例子**：用 2～4 维的小数字把这一章的推导重新算一遍，画面逐步显示中间结果（来自 MLA 那期）。
- **比较要公平**：拿同类方案在同样条件下比（例如同样的 KV cache 预算下 MLA 对 GQA/MQA）；作为上限的参照不是对手；论文自己报告的结果要注明出处。

## 代码是主线（这是本系列的特色，保留并加强）
- 每个概念都要落到几行 PyTorch 代码上，代码逐章累积，最后合成完整模块。
- 旁白讲**代码为什么这么写**，不念代码本身；屏幕负责展示代码和真实输出。
- 所有数值、形状、True/False 都来自真实运行（py/values.json），不手编。
- 关键处用 `assert` / `torch.allclose` 对照官方实现验证，屏幕上展示结果。

## 句子格式
- 一句 = 一个画面节拍，朗读时长约 3–8 秒（约 15–40 字）。
- 口语、短句，像老师讲课；主语清楚，少用长定语。
- 字幕文本（屏幕显示）和朗读文本分开：符号、代码、公式在"读："里写成读法，
  如 `x @ x.T` → "x 乘 x 的转置"，`k.transpose(-2, -1)` → "k 点 transpose 负二负一"。
  简单的读得通的不需要"读："。
- 每句必须写"画："，说明这一句屏幕上出现什么（审阅时用户据此判断画面是否合理）。

## 用户反馈过的问题（第一版 GQA 视频）
- **AI 味**：冒号模板句（"结果：""实测：""缓存账："）、"关键是/正好/好在/这就引出"、过于工整的"第一步第二步"、"不是……而是……"对仗。写完用 humanizer-zh 润色。
- **口语化套话**：不用"算一笔账""算账""账本""聊聊""唠唠""干货""硬核""拆解""搞懂""秒懂"这类词。直接说要算什么，例如"KV cache 占多少显存"。
- **字幕符号**：字幕里少用 `a_ij`、`n_kv_heads` 这类下划线写法，用 aᵢⱼ、"KV 头数"等；代码留在画面里。
- **多音字**：TTS 会把"第 i 行"读成 xíng，"读："里写成"航"。
- **事实核对**：举真实模型的例子前，确认它的真实结构（是 MHA 还是 GQA、头数、层数）。
- **时长**：按大纲阶段和用户约定的时长（默认每集 8–12 分钟；用户另约定时以约定为准），长内容拆成分集。

## 向 RethinkFun 学的讲法（用户喜欢的 UP 主，分析见各项目 research/rethinkfun/analysis.md）
- **骨架**：点题 → 完整走一遍标准/朴素做法 → 指出瓶颈（给具体数字）→ 核心想法 → 单独拆难点 → 公式/代码逐行讲 → 结果。
- **先让朴素做法失败**：新组件要被问题逼出来，例如"如果直接这么做，你会发现训练不起来"，再讲解决办法。
- **具体的自问自答**："那位置信息从哪来？""为什么是 4？"——问题要具体，紧跟答案；不要空泛的"那么问题来了"。
- **有记忆点的数字**：用真实规模说明问题有多严重（N×M → N+M、状态数比宇宙原子还多），数字必须来自 values.json 或可核对的来源。
- **主动交代简化**："为了讲解方便，这里先不考虑多头和 scale，后面再加上。"
- **旁白解释图例**：颜色、箭头、虚线第一次出现时说清含义（"蓝色是 Q，绿色是 K，橙色是 V"）。
- **比喻**（若用户允许）：一句话，只为让一个结论好记，说完立刻回到正题。
- **开场钩子**：可以连续提两三个本集会回答的具体问题，再说"这一集就来回答这几个问题"。
- **语言**：主语用"我们"；"可以看到""也就是""比如"是正常连接词；结尾一句话求三连即可。
